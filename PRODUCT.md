# Product

## Register

brand

## Users

Backend engineers, performance-minded reviewers, Rinha de Backend participants, and hiring or collaboration visitors who need to understand whether this .NET implementation is credible, reproducible, and technically interesting. They arrive from GitHub, search, benchmark discussions, or direct links and expect proof quickly.

Visitors are usually scanning first, not reading deeply. They want a fast answer to three questions: what was built, why it is impressive under the challenge constraints, and where the implementation evidence lives.

## Product Purpose

This site presents `rinha2-back-end-dotnet` as a high-performance .NET 9 Native AOT implementation of Rinha de Backend 2024/Q1. It turns repository facts, benchmark reports, architecture notes, and documentation into a polished public proof surface.

Success means a visitor can understand the performance claim, inspect the constraints, reach the documentation or GitHub repository, and trust that the results are backed by CI and archived reports. The homepage should act as an engineering showcase. The docs should act as a usable field manual.

## Brand Personality

Precise, battle-tested, and slightly irreverent.

The voice should feel like a constrained-systems lab console, not a generic SaaS landing page. The current line, “Runs on Every OS. Even Windows.” is part of the brand: confident, technical, and playful without losing credibility.

## Anti-references

- Generic AI dark landing pages with gradient text, decorative glow, glass cards, and repeated metric cards.
- Terminal cosplay: green-on-black hacker aesthetics, fake shell output, and monospace everywhere without hierarchy.
- Corporate .NET brochure design: safe blue blocks, stock icons, and bland “enterprise-ready” copy.
- Benchmark dashboards that show numbers without methodology, provenance, or links to the evidence.
- Documentation dumps where every section has the same visual weight and the user cannot tell where to start.

## Design Principles

1. **Evidence before decoration.** Every visual move should help expose proof: constraints, architecture, benchmark results, CI runs, reports, and source links.
2. **System interface, not costume.** Use console, runbook, and infrastructure motifs only when they structure real information.
3. **Make the impressive parts impossible to miss.** The core proof points, throughput, latency, success rate, resource budget, and Native AOT architecture, must appear before the visitor has to hunt.
4. **One aesthetic, multiple information densities.** The homepage can be cinematic and high contrast. The docs must stay readable, searchable, and calm while sharing the same dark .NET/system language.
5. **Preserve the edge.** Keep the witty Windows line and the constrained-systems attitude. Polish should not make the site feel corporate.

## Accessibility & Inclusion

Target WCAG AA for text and interactive controls. Preserve keyboard access and visible focus states for navigation, search, drawer controls, CTAs, report links, and code-copy controls. Respect `prefers-reduced-motion` across homepage, docs, and reports. Do not rely on color alone for status or benchmark outcomes. Keep long-form documentation readable with controlled line length, clear heading hierarchy, and copyable code blocks.
